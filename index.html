              Global calibration: MODIS → VIIRS NOAA-20

              For each country, VIIRS = k × MODIS is fitted on monthly fire cell-days from April 2018 to 2025, when both sensors observed. It is tested by leaving out one year at a time, and by fitting on 2018–2023 and predicting 2024–2025. Countries with too few fires use the pooled global k.

                  Data & Methods

                  The data behind BuriningView, how the sensors are harmonized, and how the calibration is tested.

                  Data sources Harmonization method Calibration results

                  Data sources

                  NASA FIRMS ↗
                  Active fire detections from MODIS Collection 6.1 (1 km) and VIIRS S-NPP (375 m).
                  NOAA Climate Prediction Center ↗
                  The Oceanic Niño Index used in fire forecasts.
                  Map imagery and terrain
                  Esri basemap, OpenStreetMap contributors, NASA GIBS Blue Marble imagery, AWS Terrain Tiles (Mapzen Terrarium), and Natural Earth boundaries.

                  Harmonization method

                  1. Count fire cell-days. Hotspots are placed on a 0.05° grid. Each cell with a fire detection counts once per day, regardless of how many pixels detect it.
                  2. Calibrate older observations. For each region, a linear model and a power-law model are fitted using the months when both MODIS and VIIRS observed, from February 2012 through 2025.
                  3. Validate across years. Each overlap year is held out in turn. The model with the lower error on held-out years converts the older MODIS counts to the VIIRS scale.
                  4. Measure departures from typical activity. Each month is compared with the median for the same calendar month across 2003–2025.

                  MODIS → VIIRS calibration

                  Each dot is one month in which both sensors observed (Feb 2012–2025). The line is the fitted model used to bring older MODIS months onto the VIIRS scale.

                  What the status means

                  • In use — the dataset drives a chart or the forecast on this site.
                  • Pulled — the file is on disk but nothing reads it yet.
                  • Available — the download route was tested, but nothing has been collected.

                  Nothing on this page changes the forecast on its own. A dataset entering the model is a separate step.

                  Does rainfall predict fire?

                  Share of the month-to-month variation in fire activity explained by the previous three months of rainfall, 2003–2025, against what the calendar month alone explains.

                  RegionRain explainsCalendar month aloneRain adds
                  Peninsular Malaysia25.2%3.9%Yes, strongly
                  Sumatra19.9%24.1%Yes, as much as the season
                  Sabah19.9%21.1%Yes, marginal
                  Kalimantan8.0%25.9%Weak
                  Sarawak1.8%48.4%No
                  Sumatra, in plain numbers. The driest tenth of three-month spells average 5,783 fire cell-days a month. The wettest tenth average 784. A 7.4× difference, measured on this project's own record.

                  Caveats

                  • Sarawak is the exception: its fire follows the calendar, not how dry the preceding quarter was. Do not claim a rainfall effect there without showing it.
                  • POWER reports monthly rainfall as millimetres per day, not per month. January's 7.6 for Sumatra means about 236 mm for the month. Convert before use or everything is off by roughly 30×.

                  How this was measured

                  Every dataset on this page was tested the same way, and the test is deliberately unkind to the model. A forecast is issued at the end of May for June to November of the same year, using only what is knowable at that moment: January to May of the target year, carried forward. The model learns from earlier years only, and the year being predicted never appears in its training set.

                  Lower is better. The baseline is the site as it runs today: the mean of the previous five years, same month, in log space.

                  What each input bought

                  All five regions together, weighted by how much fire each one actually carries.

                  Inputs given to the modelTypical errorChange
                  Seasonal pattern only (the baseline)67.1%—
                  + El Niño + drought code49.0%−18.1 pts
                  + El Niño alone49.7%−17.4 pts
                  + rainfall alone54.6%−12.5 pts
                  + drought code alone63.1%−4.0 pts
                  + Indian Ocean Dipole alone67.5%+0.4 pts, no help
                  All four together67.0%−0.1 pts, no help
                  Two is the ceiling, not four. Adding every dataset at once lands back where the model started. With roughly ten usable training years, each extra input costs more in noise than it returns in signal. El Niño plus drought code is the pair that works.

                  Best input for each region

                  The same test, run region by region. The winning input is not the same everywhere.

                  RegionBest inputTypical errorBaselineGain
                  SarawakDrought code34.8%46.2%−11.4 pts
                  SabahDrought code36.0%42.8%−6.8 pts
                  KalimantanEl Niño + drought code48.1%55.1%−7.0 pts
                  SumatraEl Niño60.4%63.0%−2.6 pts
                  Peninsular MalaysiaEl Niño31.6%31.7%−0.1 pts, no gain
                  Sarawak was not undriven, it was mis-driven. The model already rejected El Niño there, scoring 47.4% against the baseline's 48.5%. Drought code cuts the same error by 11 points. The region always had a driver; the site was looking at the wrong one.

                  Read this before quoting any of it

                  • Do not compare these numbers with the 38.2% in the README. That figure spans all twelve months and uses the year's actual El Niño value, which is not known when the forecast is made. This table covers the dry-season half only, with no foreknowledge. They are different measurements of different things.
                  • Choosing the winning input per region is mild hindsight. The pick is made after seeing the backtest, which flatters the result. The existing use_enso flag already works this way. It is disclosed here rather than hidden.
                  • None of this is wired into the model yet. forecast.py still runs on El Niño alone, and it still reads the target year's own index. The numbers above describe what the data is worth, not what the site currently does.

                  Steps

                  1. Rebuild the fire record.
                    python Clean.py --modis "modis_2000-2025_*.csv" --viirs "viirs-snpp_2012-2025_*.csv" --out Clean_dataset\clean_hotspots.csv
                  2. Recalibrate MODIS to VIIRS.
                    python calibration.py --inp clean_hotspots.csv
                  3. Pull the climate data.
                    python pull_power.py — 28 parallel requests, no key, about six seconds.
                  4. Re-run the rainfall check.
                    python check_power_vs_fire.py — reproduces the numbers on the Climate data page.
                  5. Pull the fire weather.
                    python pull_gfwed.py — 288 monthly files, ten at a time, about ten minutes. Resumable: re-run it and it continues where it stopped.
                  6. Re-run the accuracy test.
                    python eval_predictors.py — reproduces every number on the What the data is worth page.

                  All four scripts sit in the project root and use the backend virtual environment.
